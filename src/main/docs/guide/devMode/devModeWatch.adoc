A bean that derives state from other beans, from configuration or from files registers a watch for the specific things it needs, on api:context.WatchableBeanContext[], and receives one batched change whenever they change. The state at startup is the first batch, so a watcher has no separate startup path, and a watch registered while a bean is being created belongs to that bean and closes with it.

NOTE: api:context.WatchableBeanContext[] and the types of the `io.micronaut.context.watch` package are public API for modules, marked `@Experimental`: a module that derives state from the context watches it here rather than listening for events, and the API may still change in a minor release. The default context is the only implementation; a module tests for it with `instanceof` and watches nothing when given another context.

[source,java]
----
@Singleton
final class RouteTable implements BeanDefinitionWatcher<RouteBuilder> {

    RouteTable(WatchableBeanContext context) {
        context.watchDefinitions(RouteBuilder.class, null, this);
    }

    @Override
    public void onChange(BeanDefinitionChange<RouteBuilder> change) {
        rebuild(change.current()); // the set after the batch; change.added() and change.removed() name what moved
    }
}
----

`watchDefinitions` and `watchBeans` watch a type, `watchMethods` the executable methods carrying an annotation, `watchConfiguration` a configuration prefix and `watchResources` the files of a resource kind by glob. A definition or method that comes back in a new generation is paired with the one it replaces, and the pair says whether only bodies changed.

A configuration watcher runs after the configuration beans under its prefix were rebound and says what it did: `APPLIED` when it changed the live bean, `RECREATE` when the bean that registered the watch must be replaced, in which case the context replaces it and the beans that received it, `REQUIRES_RESTART` when nothing short of a restart applies the change.

[source,java]
----
@EachBean(DatasourceConfiguration.class)
HikariDataSource dataSource(DatasourceConfiguration configuration, WatchableBeanContext context) {
    HikariDataSource dataSource = new HikariDataSource(configuration);
    String prefix = "datasources." + configuration.getName();
    context.watchConfiguration(prefix, change -> {
        if (change.touches(prefix + ".url")) {
            return ConfigurationWatcher.Outcome.RECREATE;         // this pool only
        }
        if (change.touchesAny(prefix + ".username", prefix + ".password")) {
            dataSource.getHikariConfigMXBean().setPassword(configuration.getPassword());
            dataSource.getHikariPoolMXBean().softEvictConnections();
            return ConfigurationWatcher.Outcome.APPLIED;
        }
        return ConfigurationWatcher.Outcome.IGNORED;
    });
    return dataSource;
}
----

A configuration watch has no first batch unless it asks for one: `watchConfiguration(prefix, watcher, true)` calls the watcher once with a change whose `initial()` holds, so that the bean reads its configuration inside the watch: at once when the context is running, or when it starts for a watch registered before, as every first batch is delivered. What it answers to that call is not acted on.

A bean that reads the definitions or configuration it derives state from, and only then registers a watch, can miss a change made in between. The first batch closes that gap: it is read after the watch is registered, so a bean that builds its state from the first batch, instead of from a read of its own, misses nothing.

* Batches reach a watcher one at a time, the first batch first, then the changes in the order they were made; no change is delivered before the first batch or alongside another, and no lock is held while a watcher runs.
* A change applied before the first batch began to be read shows in it and is not delivered again; one applied after it was read is delivered after it.
* Only a change applied while the first batch was being read can show in it and be delivered after it too, so a watcher treats an addition it already has, or a removal of something it never had, as nothing to do.

[source,java]
----
@Singleton
final class SerializerRegistry {

    private volatile List<BeanDefinition<Serializer>> serializers = List.of();

    SerializerRegistry(WatchableBeanContext context) {
        // no read of its own: the first batch is the read, and every change after it follows
        context.watchDefinitions(Serializer.class, null, change -> serializers = sort(change.current()));
    }
}
----

A cache keyed by class is not a set of beans: it forgets what a reload retires. `watchClassChanges` gives the watcher every api:context.reload.ClassChangeEvent[] the launcher publishes, ahead of the listeners of the event, with the same ownership as the other watches. Classes only change in development mode, so outside it the call registers nothing and returns an inactive watch, and the module needs no listener bean gated on development mode.

[source,java]
----
context.watchClassChanges(change -> cache.keySet().removeIf(change::isStale));
----

When a change cannot be applied to a bean in place, the watcher asks the context to recreate it: `recreate(bean)`, or `recreate(Type.class, qualifier)` for the singleton of a type, destroys the beans that received it, as the dependency graph records them, destroys the bean and creates it again, and the dependents are created again when next requested, on top of the new instance. Both return whether anything was recreated, which a prototype, a bean of a custom scope or a singleton registered at runtime never is. They are meant for development-time watches: the dependents are known only when the context tracks bean dependencies, which by default only a context in development mode does (`ApplicationContextBuilder.trackBeanDependencies(true)` turns it on elsewhere), and a context that does not recreates nothing and returns false, rather than leave dependents holding the destroyed instance.

[source,java]
----
context.watchClassChanges(change -> {
    if (serializers.stream().anyMatch(change::isStale)) {
        context.recreate(SerializerRegistry.class, null);
    }
});
----

Resources are watched the same way: a template engine registers `watchResources(ResourceSelector.of(ResourceKind.VIEWS, "**/*.html"), change -> ...)` and clears what the change affects, rather than filtering an event every engine receives.

NOTE: Existing api:context.processor.ExecutableMethodProcessor[] and api:context.processor.BeanDefinitionProcessor[] beans keep working. The context feeds them what is added after startup, through an adapter that sees additions only, which is also how the launcher tells that such a processor cannot follow a reload.

=== Testing a module against a reload

`micronaut-dev-tck` is a small TCK a module runs in its own build: a harness writes a project into a directory, compiles it with the annotation processor on the test classpath, starts it through the development runtime in the test's JVM, and reloads it after an edit, so a test sees two real generations. The module under test is on the test classpath, so it is parent-tier, as it is for an application; the sources the test writes are the reloadable tier.

[source,java]
----
try (ReloadHarness harness = ReloadHarness.inDirectory(tempDir)) {
    harness.source("example.Greeter", "package example; @jakarta.inject.Singleton public class Greeter implements Greeting { public String greet() { return \"one\"; } }");
    harness.start();
    harness.source("example.Greeter", "package example; @jakarta.inject.Singleton public class Greeter implements Greeting { public String greet() { return \"two\"; } }");
    harness.reload();
    ReloadTck.assertFollowsReload(harness, context -> context.getBean(GreetingRegistry.class).current());
    ReloadTck.assertRetiredGenerationsCollected(harness);
}
----

api:dev.tck.ReloadTck[] holds the assertions: `assertFollowsReload` checks that what a registry hands out after the reload is the new generation's, and names the fix when it is not (watch the definitions, or resolve through the context on use); `assertRetained` checks that a bean the module retains is the same instance the new generation serves; and `assertRetiredGenerationsCollected` checks that no retired generation is reachable once the garbage collector ran, which a static cache or an unstopped thread would prevent. Add `micronaut-dev-tck` and `micronaut-inject-java` to the test classpath to use it.
